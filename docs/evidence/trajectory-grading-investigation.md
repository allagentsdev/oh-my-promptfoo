# Trajectory goal grading investigation

Investigated 2026-11-06; research only. No WTG files changed and no live judge invoked.

## Final decision: not planned (2026-11-10)

The owner chose not to proceed with a dedicated trajectory grading mode. The experimental implementation, tests and evidence are retained for reference, not for release or merge. It implements `llmAssert`'s `config.mode: trajectory`, preserves batching and existing scoring, and uses a local implementation of Promptfoo's native summary behavior. The design discussion below records the earlier proposal.

The investigation did not establish enough demand for this particular interface to justify maintaining a separate native-style summarizer. This is not a claim that semantic trajectory grading is uncommon. Native `trajectory:goal-success` already supports single-goal grading, and consumer-authored JavaScript can project evidence into an existing batched rubric. A mock-judge experiment verified that both a metadata-based assertion transform and a trace-aware JavaScript assertion preserve one batched judge request without the new mode. Ordinary transforms receive provider metadata, while JavaScript assertions receive `context.trace`.

The simple projection approach puts labelled answer and evidence fields inside one graded output bundle. It does not provide the experiment's separate `<Output>` and `<Trajectory>` framing or its shared normalization and omission policy. No generic wrappers or evidence envelopes were introduced into WTG, and no WTG files were edited.

Implementation verification on 2026-11-09: typecheck, lint, build, 18 focused tests and npm/pnpm packed-consumer checks passed. The broad suite recorded 961 passes, five failures and five skips; all five failures passed in an isolated one-worker rerun. The internal npm registry connection failed; the packed-consumer check passed using a command-scoped public-registry override. No live judge or model-quality run was performed.

## Design explored before withdrawal

**Support an opt-in batched goal-success mode on `llmAssert`, with batching mandatory.** The clarified requirement rules out delegating each component to a separate native assertion. Adapt the system prompt to judge each named criterion against the final answer and a separate untrusted trajectory summary, while retaining one request and the existing per-component reply format. This follows `llmAssert`'s established role as an adaptation of a native judge prompt for batching. The original recommendation against any flag overstated the obstacle: native handler delegation loses batching; adapting the prompt does not.

The mode should change the grading subject from the answer alone to the recorded run and answer. Update both the opening instruction and the requirement for reasons to cite available evidence; merely appending a trace would leave the current answer-only instructions contradictory. Adopt native goal-success's end-to-end-success instruction while preserving each criterion's exact scope, polarity and conditions. Keep the candidate in `<Output>`, named criteria separately identified, and the trajectory in a separately labelled untrusted block. Keep skill routing and deterministic action checks separate. This does not recreate WTG's removed generic envelopes or require WTG wrappers.

Keep existing judge inheritance, component weights, result format, retry behavior and explicit `scoring` selection. Default binary mode still requests 0/1 with threshold 1; graded mode permits native-style partial credit. The trajectory option should not silently switch scoring policy. Exact native behavior is necessarily adapted at the multi-component reply/scoring contract, as it already is for batched `llm-rubric`. Keep the option disabled by default, with no changed trace requirement or extra judge request for existing configurations.

The initial proposed field was assertion-level `config.mode: goal-success`. The owner noted that the name did not communicate inclusion of tool activity, so the experiment uses `config.mode: trajectory`, with `rubric` as the default when omitted. `scoring: binary | graded` remains an independent choice about numeric credit. One mode applies to the whole batch; no per-criterion mode or parallel boolean alias was added.

One integration seam remains: `summarizeTrajectoryForJudge` is exported from its internal source module, but is not exposed by the inspected Promptfoo public root API (`src/index.ts`). Prefer an upstream public summary helper over private package imports or extracting a summary by running a paid native judge. If a local summary is chosen instead, specify and verify its parity rather than claiming automatic upstream alignment. Missing trace should fail clearly; truncation and incomplete evidence must remain visible and never prove absence. Defer the same flag on `agentAssert` until the prompt consistently permits recorded-run evidence alongside inspected workspace outcomes; do not replace its workspace judge or permission policy.

The public scoring hook already supports WTG's binary-vote aggregation policy. That concern remains separate from changing judge evidence or instructions.

### Tool and provider evidence already available

The package already exports `tool-called`, `tool-not-called`, `skill-not-loaded`, `workspace-file`, `llmAssert`, `agentAssert` and `withAssertions` (`assertions.ts:10–31`). Its durable `toolInventory` records call identities, names, bounded arguments, start/end times, success and completeness; it does not contain returned tool bodies (`tool-inventory.ts:4–28`). Deterministic tool assertions require a certified complete inventory and support argument/shell selectors and invocation ordering (`tool-assertions.ts:11–20,141–181`). This is stronger about completeness than an ordinary native trajectory, though an invocation alone is not proof of returned content or final state.

Copilot SDK events supply start arguments and completion success to the inventory. Replayed trace starts carry tool names/arguments; ends carry failure status but no returned content (`delegate-runner.ts:727–789`, `protocol.ts:377–408`). Native summary command text for Copilot `bash`/`powershell` needs `tracing.commandToolNames: [bash, powershell]`; otherwise the goal judge can see only the generic tool name. Native Codex spans can carry `codex.command`, MCP input and error status; available attributes are replayed under the row trace (`delegate-runner.ts:70–116`; `promptfoo/src/providers/openai/codex-sdk.ts:1347–1364,1472–1502,1691–1714`). Codex command-output span events are not replayed by this package's attribute-only bridge, and goal summaries omit such bodies regardless. Copilot and Codex therefore share a grading entry point, not an identical evidence contract.

Native Codex inventories explicitly remain incomplete (`native-tool-inventory.ts:47–58`) even when useful spans/raw tool items are retained. Copilot completeness has SDK idle/skill/subagent checks and bounded collection. Do not upgrade missing/truncated trace evidence into proof of absence or strict completion order. Native skill records/checks remain separate; neither semantic goal grading nor an inventory's SDK-loaded names substitute for verified `metadata.skillCalls` (`docs/provider-guide.md:90–136`).

### Binary scoring corroboration

The existing public `withAssertions` integration adds required-check vetoes; required votes are excluded from the ordinary weighted denominator, and a failed required vote yields score 0. That changes acceptance policy rather than normalizing an ordinary goal vote (`assertion-integration.ts:31–90,172–180`). With no required gates it preserves raw fractional scores.

A focused mock call into the real shared `gradeRubric`, with a component threshold of 1 and judge reply `{pass:true,score:0.6}`, returned `pass:false,score:0.6`. Thus this repository's binary mode enforces the pass bar but does not deterministically coerce numeric scores. Existing tests corroborate fractional near-misses in default binary mode (`tests/assertions.test.ts:376–407`; `tests/agent-assert.test.ts:406–437`). Switching native goal checks to either batched assertion does not guarantee binary aggregation.

Additional read-only mock experiment, Node `v22.22.1` matching `.node-version`: failed goal `.6` plus action `1` at case floor `.75` returns `.8/pass` through `requiredScore` without gates, `0/fail` with the goal required, and `.5/fail` through WTG's existing `case-score.mjs`. These are three distinct policies. WTG's existing `binaryGoals` normalizes only threshold-1 native goals, recomputes enclosing groups, and preserves raw diagnostic components while supplying normalized aggregate/named scores (`WTG.AI.Prompts` main `d63fb3db5`, `evals/.templates/case-score.mjs:44–102`). Nothing in this investigation changes that scorer or its policy.

## Trace selection and information loss

The goal handler accepts `assertionValueContext.trace`, not oh-my-promptfoo recorded-call metadata or a workspace. The native assertion pipeline loads by evaluation trace ID with `getTrace(..., {sanitizeAttributes:false})`, polls for a stable nonempty span count, and snapshots before running assertions. `getTrace` reads every stored span with that trace ID; this path has no explicit target-subtree selection, unlike the separate configurable `getSpans` context path. Missing trace throws. An existing trace with `spans: []` passes the handler's presence check and can reach a judge; partial or delayed traces have no completeness guarantee.

References: local `src/assertions/index.ts:189–232,489–500,863–873`; `src/tracing/store.ts:528–559,660–733`; upstream [`trajectory.ts:41`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/trajectory.ts#L41).

`extractTrajectorySteps` sorts spans by start time, end time, then original index and classifies command/tool/search/reasoning/message/span. The **judge summary** includes only index, type, name, optional spanName and nonzero status. It excludes tool arguments, tool results, arbitrary attributes, message content, reasoning text, and file contents. Command text and search queries may survive because they become step names. Consecutive equal steps collapse; beyond 24 compacted steps, only the first 12 and last 12 remain, with an `omittedCount` marker. A long middle section can contain the decisive action or failure.

Evidence: [`trajectoryUtils.ts:310`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/trajectoryUtils.ts#L310), [`trajectoryUtils.ts:462`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/trajectoryUtils.ts#L462), [`trajectoryUtils.ts:498`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/trajectoryUtils.ts#L498). The goal schema itself provides only `goal`, with no per-assertion span selector.

## Judge inheritance, output and transport

Native goal uses standard assertion provider/rubricPrompt overrides, then test options and standard default-provider resolution. It does not automatically choose the evaluated Copilot/Codex provider as its judge. The shared executor uses `llmRubricProvider || gradingJsonProvider` when a default provider is needed; its provider context has `isGrading:true`, judge prompt/vars and original-provider context when supplied. Native goal does not take `llm-rubric`'s special redteam remote-grading branch or its image/audio normalization/attachments. Provider support can also depend on the grader label: `src/providers/typesafe.ts:38,214–218` explicitly rejects `trajectory:goal-success` and `agent-rubric` while supporting `llm-rubric`/classifier (also present in npm 0.125.1). A custom inherited `rubricPrompt` replaces the goal prompt, so a rubric-only template can silently omit goal/trajectory unless authored for them.

Evidence: local `src/assertions/utils.ts:40–89`, `src/assertions/index.ts:662–699`; [`rubric.ts:876`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/matchers/rubric.ts#L876); `src/matchers/providers.ts:139–179,210–295`; `src/matchers/llmGrading.ts:200–255,269–297`.

Both local model graders return `pass`, numeric `score`, `reason`, token usage and metadata including rendered grading prompt. With a judge verdict present, an assertion threshold only further constrains pass (`pass && score >= threshold`); it preserves the raw score. Without a verdict, a finite score derives pass using threshold or `score > 0`. Native goal has no binary-score option. Its inverse changes real verdicts into binary scores, but preserves grader errors; using double negation as normalization is not a public scoring API.

Evidence: [`rubric.ts:837`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/matchers/rubric.ts#L837), [`rubric.ts:938`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/matchers/rubric.ts#L938), `src/assertions/trajectory.ts:651–667`; existing `test/matchers/trajectory-goal-success.test.ts:79–116` explicitly expects a failing fractional score to remain fractional.

## Scoring concern and existing public mechanisms

Confirmed: a native goal failed at assertion threshold 1 still contributes its fractional score to case/group weighted means. A numeric case or assertion-set threshold **overrides** component pass/fail, using that mean. Wrapping the goal in an `assert-set` with threshold 1 retains the fraction; changing weights does not binarize; assertion `transform` transforms provider output before grading, not the grade. Setting weight 0 discards the vote and forces the individual assertion to pass. Replacing the judge prompt with binary instructions asks the model to comply but does not enforce binary numeric output.

Public `assertScoringFunction` already provides the extension mechanism: the callback receives component results and can map selected native goal verdicts to binary votes, recompute enclosing weighted groups and retain the case floor. No new assertion flag is required to obtain that mechanism. There is no built-in declarative native-goal binary option. A correct consumer scorer must preserve root/group weights, distinguish flattened duplicate child entries, retain raw diagnostic grades, handle grader errors separately, and decide whether normalization changes metrics as well as aggregate score. This is a consumer aggregation policy, not a richer evidence contract.

Evidence: [`assertionsResult.ts:252`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/assertionsResult.ts#L252), [`assertionsResult.ts:314`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/assertionsResult.ts#L314), [`assertionsResult.ts:384`](https://github.com/promptfoo/promptfoo/blob/67651ef13adb9a3b621335a56bcc3264b7c9b3d1/src/assertions/assertionsResult.ts#L384); local `src/assertions/index.ts:470–475,723–728,945–960`; public `ScoringFunction` context is typed in `src/types/index.ts:925–943`. Online scoring documentation describes the callback and common-scale mapping, but its displayed interface omits the component-results field that source supplies.

Focused zero-judge experiment: `/tmp/promptfoo-trajectory-score-experiment.mts` imported the real local `AssertionsResult` and `summarizeTrajectoryForJudge`. Results: failed goal score 0.6 plus passed action score 1, equal weights and case floor 0.75 => **pass, 0.8**. Singleton assert-set at threshold 1 => **fail, 0.6**. Public scoring callback mapping component verdicts => **fail, 0.5**. Thirty distinct tool spans => first 12 + omitted 6 + last 12, with synthetic argument/result values absent. No repository source files or database were changed by this experiment.

Read-only consumer corroboration supplied by the parent: `WTG.AI.Prompts` main `d63fb3db5`, `evals/.templates/case-score.mjs:44–65`, already uses the public scorer to normalize threshold-1 native goals and recompute groups before the unchanged case floor. I inspected that file without modifying it. This corroborates that the public hook is sufficient; whether a reusable library scorer is preferable is a separate API decision owned by the parent investigation.

## Limits and remaining questions

- No real Copilot/Codex parity run was performed. Backend-independent native judging does not establish equal telemetry completeness or names.
- Capability/version evidence: trajectory goal success was introduced in upstream commit `6567fdaf0b381e65110451f802222fc0f861613a` (2026-03-13, #8040); all six locally available WTG `v0.124.1-wtg.*` tags contain it. The checkout package identifies itself as `0.124.1-wtg.6`. The official npm `promptfoo@0.125.1` tarball (the project's pinned dev dependency) was inspected in memory, with selected JS written only to `/tmp`: its bundled `index.cjs` contains the native handler, same goal matcher/prompt/summary, and `assertScoringFunction` path. This establishes availability there, not a complete peer-version support floor. Sources: [npm metadata](https://registry.npmjs.org/promptfoo/0.125.1), [introduction commit](https://github.com/promptfoo/promptfoo/commit/6567fdaf0b381e65110451f802222fc0f861613a).
- A provider may supply message/command content through names or status messages; omission of structured bodies is not blanket redaction.
- Decide whether missing/truncated evidence should cause an error, failure, or lower-confidence semantic result. Native goal currently has no completeness contract.
- Decide whether consumers want binary checklist votes or native partial-credit task success. A threshold alone cannot express both.
