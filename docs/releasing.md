# Releasing to npm

## First release as oh-my-promptfoo

`oh-my-promptfoo` is a new npm package. Version 1.6.0 is its first stable release. The Release Please workflow treats this package separately from releases under earlier names.

The first release was tagged `v1.6.0` at reviewed main commit `50c5684` and published with `npm login --auth-type=web` and `npm publish ./packages/oh-my-promptfoo --access public --tag latest --provenance=false`. Packed-package checks, installed-registry consumers, and Promptfoo E2E passed before the GitHub release became public.

Trusted publishing is configured for the renamed repository's preview and stable workflows. The earlier npm packages have been removed from the registry; `oh-my-promptfoo` is the installable package.

## Later releases

After the initial stable release, Release Please prepares version and changelog pull requests. While one is pending, eligible pushes to `main` publish an installable `X.Y.Z-next.N` preview under npm's `next` dist-tag and create a matching GitHub prerelease from that `main` commit. Merging the release PR creates a draft stable tag and GitHub release, then dispatches [publish.yml](../.github/workflows/publish.yml) at that tag. Publish runs source and packed Promptfoo checks, publishes stable under `latest` with npm OIDC, verifies the installed registry version, and only then makes the GitHub release public. `next` previews are not candidates from the eventual release-PR merge commit; post-publication registry checks can fail after `latest` is already immutable.

1. The first `1.0.0` of the old `@allagents/promptfoo-integration` package was tagged at reviewed `main` commit `e10a9d3` and published by the GitHub-hosted OIDC workflow. Public CI, packed consumers, and installed-registry Promptfoo E2E passed. A separate private target check is not an npm or public-package release prerequisite; run private dogfooding when the private deployment needs it.
2. For subsequent releases, use Conventional Commits. Release Please opens a draft PR updating both manifest versions and `CHANGELOG.md`; its workflow synchronizes `pnpm-lock.yaml` and marks the PR ready only after that commit succeeds. Review the version and CI checks before merging. GitHub does not trigger PR checks from PRs created with its default `GITHUB_TOKEN`; to avoid manual validation, configure the repository's `RELEASE_PLEASE_TOKEN` GitHub credential. This credential is not an npm token.
3. On `main` pushes while a release PR is open, `release-please.yml` validates a new prerelease for `next`. Immediately before publication, it rechecks the release PR and source ancestry. If the PR closed, merged, or changed head during validation, the preview succeeds as superseded with a notice; it skips npm publication, registry consumer checks, and GitHub preview tag/release creation. A still-current PR remains eligible. Malformed GitHub responses, API failures, invalid refs or versions, source-identity mismatches, and real validation failures still fail the job. Merging the release PR tags the reviewed merge commit and dispatches `publish.yml` automatically. Publish validates that stable tag is reachable from `main`, checks local and packed consumers, publishes under `latest`, verifies registry consumers and Promptfoo E2E, then publishes the draft GitHub release.

4. If publishing fails before npm accepts the package, the GitHub release remains draft. npm may accept a package before its version and dist-tag become queryable; the publisher waits up to five minutes for indexing rather than immediately treating that lag as a failure. Rerun `publish.yml` for the same stable tag after a transient failure: an already-published version is verified, never republished. If registry consumer checks expose a real defect after npm acceptance, that version is immutable; fix it on `main` and publish a corrective version. Rerun `release-please.yml` only if dispatch itself failed.

npm trusted publishers for organization `allagentsdev`, repository `oh-my-promptfoo`, GitHub environment `npm` are configured for `release-please.yml` (`next` previews) and `publish.yml` (stable `latest`), each with direct `npm publish` allowed. Both jobs need `id-token: write` and npm 11.6.2; no npm token is stored in GitHub. See [npm's trusted-publishing setup](https://docs.npmjs.com/trusted-publishers/).

The initial `1.0.0-rc.1` was published manually without provenance. `1.0.0` was the first stable OIDC release from commit `e10a9d3`; an immediate npm indexing read failed, and the successful rerun verified the accepted package without republishing. `1.0.1-next.11` became the first automatic `next` preview, and merging Release Please PR #13 published `1.0.1` under `latest` from its reviewed merge commit. Those three OIDC-published versions have signed provenance; the manual `rc.1` does not. Published version bytes and metadata cannot be changed retroactively.

The [Validate workflow](../.github/workflows/validate.yml) gives each normal validation, packed Promptfoo E2E, and Linux acquisition job a 15-minute timeout. A stalled compiler, dependency install, or acquisition check fails within that bound rather than occupying a runner for GitHub's six-hour default. Release orchestration and publication keep their separate, longer job budgets and existing indexing retries.

`pnpm pack:check` also starts the real declared Copilot SDK and its bundled runtime in
each isolated npm and pnpm consumer. The smoke checks the runtime's reported version
against the SDK's `copilotCliVersion`, a real protocol/ping round trip, and clean shutdown.
It uses a fresh home directory, excludes credentials and CLI-path overrides, and never
creates a model session or requests inference. This complements the deterministic SDK
fixtures; SDK and CLI package version numbers do not have to be identical. The runtime
test has a 30-second execution timeout and a five-second cleanup timeout.

## Dependency maintenance

Development and CI use pnpm and the root `pnpm-lock.yaml`; publishing to npm does not change the package manager. Dependabot uses the `npm` ecosystem, which maintains the pnpm lockfile, for workspace dependencies and `github-actions` for workflow actions. Updates arrive weekly, with minor/patch package updates grouped and major package updates left separate. Node types stay on major 22 until the runtime floor changes.

The [Dependency Audit workflow](../.github/workflows/dependency-audit.yml) runs daily, on dependency-changing pull requests, and manually. It runs `pnpm audit --audit-level moderate` against the lockfile. Moderate, high, or critical advisories fail the job; a registry or network error also fails rather than reporting a clean audit. It then installs the frozen lockfile with dependency scripts disabled and exercises the Forge acceptance regressions below.

GitHub supports both version-update and security-update PRs for pnpm through the `npm` ecosystem ([supported ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)). Dependabot does not manage override-only declarations, so scheduled audits still detect newly published advisories even when no code changes.

Before merging a dependency update, run the audit and the normal validation checks. Review SDK peer requirements in `packages/oh-my-promptfoo/package.json` alongside root development pins and packed-package compatibility. `pnpm audit` lists the vulnerable paths and `pnpm why <package>` shows the parent ranges that block a fix; do not force major upgrades or add advisory exceptions just to make CI green. An advisory with no published fix remains a merge blocker until a reviewed remediation or explicit risk decision is available.

The lockfile resolves `ip-address` to `10.7.4` for [GHSA-rxp7-6hxx-x8q5](https://github.com/advisories/GHSA-rxp7-6hxx-x8q5), which fixes quadratic-time IPv6 zone parsing. This patch fits the existing parent ranges and needs no override. Re-run the audit before merging even when an earlier check was green: new advisories can invalidate that result.

### Release intent

Build/dev-only dependency updates may use a non-releasing `chore` title. Updates that change bundled or runtime dependencies, or any public peer contract, need a releasable pull-request title: `fix`, `deps`, `feat`, or `perf`, or explicit breaking Conventional Commit intent in the title, such as `chore(deps)!: ...`. This includes bundled `diff`, `ignore`, `import-meta-resolve`, `jsonc-parser`, `@opentelemetry/*`, and the public SDK peers even when a development pin changes with them. A dependency's location in the root development manifest does not make a shipped change dev-only.

The dependency release policy checks dependency changes against the PR title before merge. Dependabot's initial title is not a release decision: rename bundled/runtime or peer updates to a releasable title such as `fix(deps): update bundled dependencies`. Keep development SDK pins aligned with public peer requirements and exercise installed consumers, not just the workspace lockfile.

### TypeScript and declaration builds

TypeScript `7.0.2` no longer exposes the legacy compiler API that `tsup` uses for declarations. The build pairs `tsdown` `0.23.1` with a parent-scoped `rolldown-plugin-dts` `0.28.7` override; `tsdown` selects Rolldown `~1.2.13`. Keep this compiler/plugin pairing rather than selecting an arbitrary latest declaration plugin: plugin `0.28.7` uses the experimental native TypeScript 7.0 CLI, while newer plugin implementations may require the TypeScript 7.1 API. See [Promptfoo's migration](https://github.com/promptfoo/promptfoo/pull/10341).

Use `pnpm build`, which invokes `node --import tsx scripts/build.ts`; the explicit loader supports Node builds without native TypeScript stripping. Keep `pnpm typecheck` as a separate gate: native declaration emission uses `--noCheck`, so a successful build does not prove the source typechecks.

### Reviewed security overrides

The private development workspace uses stock Promptfoo `0.125.1` and reviewed root overrides while upstream dependency pins or ranges block the fixes. The public peer range also accepts `0.125.x`; packed Promptfoo E2E uses `0.125.1`:

* `get-uri@8.0.1` uses `basic-ftp@6.2.3`, including the directory-listing and PASV parsing fixes. The consumed download/list API is compatible; the deliberate security change is that PASV transfers to a different non-loopback host are rejected. FTP PAC deployments that require separate transfer hosts are not compatible with this override. `get-uri` cannot opt back in and has a pre-existing unhandled download-rejection path; use same-host/EPSV FTP or an HTTPS PAC URL instead. Replace the override when the upstream proxy-agent/get-uri chain ships compatible secure ranges ([upstream PR](https://github.com/TooTallNate/proxy-agents/pull/500)).
* `node-forge` uses the genuine source commit `db05494352dd3c9a5a07c5270333dcc78866cad2` from [Forge PR #1159](https://github.com/digitalbazaar/forge/pull/1159), which rejects noncanonical RSA DigestInfo encodings for CVE-2026-85393. This is an immutable, unmerged contributor commit, not an official patched release; its `1.4.1-0` version comes from upstream. The earlier element-count-only proposal does not cover all bypasses. Replace this source pin once an official release includes the canonical-encoding fix and passes the same regressions.
* `@github/copilot-sdk@1.0.22>zod` uses `4.6.7` for [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). Oversized collections with a leading upper-size constraint now fail before element validation. Unconstrained schemas still accumulate validation issues; this is not a global validation-memory cap. The SDK's consumed structural schema API is retained, and its public peer pin stays `1.0.22`.
* `@earendil-works/pi-coding-agent@1.3.0>undici` uses `8.12.2`, whose [security fixes](https://github.com/nodejs/undici/releases/tag/v8.12.2) cover orphaned response-stream errors, retained EventSource parser state and mixed-case SRI algorithms. Its Node floor remains `22.19.0`, below this package's floor. The included proxy change makes `NO_PROXY=*.example.com` match subdomains but not the apex `example.com`; deployments relying on the previous wildcard behavior must review that difference.
* `@azure/identity@4.14.0>@azure/msal-node` uses the genuine published `7.1.1` for [GHSA-xcx6-jx8p-x3h5](https://github.com/advisories/GHSA-xcx6-jx8p-x3h5). This is a reviewed cross-major substitution, not a general MSAL 6-to-7 compatibility claim: Promptfoo's enumerated credential paths retain their consumed APIs, Identity does not supply the removed interactive `responseMode`, and MSAL 6 already defaulted to `form_post`. Network-isolated regressions exercise real client-secret token acquisition, trusted authorization-code redemption, state validation and rejection of unsupported instance-aware confidential-client inputs. Custom interactive clients relying on query-mode loopback responses are not supported by MSAL 7; broker, sovereign-cloud and live credential matrices are not claimed as exercised.

A registry advisory audit does not cover Git resolutions. A clean registry audit therefore does **not** establish that Forge is secure. `tests/dependency-security.test.ts` resolves the actual Promptfoo → JKS → Forge implementation and checks valid signatures, changed messages, both canonical parameter forms, extra sequence elements, non-NULL/nonempty parameters, nonminimal lengths, and trailing bytes with normal padding checks. The dependency-audit workflow and normal validation run these cases. Maintainers must also review new upstream Forge advisories and releases while the source pin remains; Dependabot does not manage override-only declarations.

The same dependency-security suite resolves the actual SDK/Identity descendant packages, rejects oversized Zod input before visiting elements, catches the undici early-close crash without masking process errors, and checks ordinary gzip/SRI and Azure credential behavior. These are behavioral regressions, not package-version assertions. Remove or retarget each parent-specific override only when an upstream supported parent declares a secure dependency and the corresponding checks pass.

These overrides apply to this repository's private workspace. They do not propagate to consumers' independently generated lockfiles or control their Promptfoo or optional SDK peer installations. Consumers must audit their own dependency graphs and apply their own reviewed remediation where parent pins still select vulnerable versions. OpenTelemetry compatibility also needs installed-consumer coverage: forcing a compatible API version in this root lockfile does not establish that Promptfoo can read a provider registered through a different API version. Root overrides live in `pnpm-workspace.yaml`; parent-scoped dependency edges use pnpm `>` selectors.

Dependency-edge overrides do not rewrite code already embedded in published packages. Pi `1.3.0`'s prebuilt CLI/RPC bundles contain an older undici implementation; the integration imports Pi's unbundled SDK entry, not those bundle entry points. This workspace remediation is not a claim that every Pi entry point, consumers' peer trees, or Node's built-in networking implementation is secured by this lockfile.
