# Releasing to npm

After the initial stable release, Release Please prepares version and changelog pull requests. While one is pending, each push to `main` publishes an installable `X.Y.Z-next.N` preview under npm's `next` dist-tag and creates a matching GitHub prerelease from that `main` commit. Merging the release PR creates a draft stable tag and GitHub release, then dispatches [publish.yml](../.github/workflows/publish.yml) at that tag. Publish runs source and packed Promptfoo checks, publishes stable under `latest` with npm OIDC, verifies the installed registry version, and only then makes the GitHub release public. `next` previews are not candidates from the eventual release-PR merge commit; post-publication registry checks can fail after `latest` is already immutable.

1. Before initial `1.0.0`, run the [private representative exact-pin gate](operations/release.md) for the reviewed commit on `main`, confirm root and public manifests both contain `1.0.0`, then create and push `v1.0.0` there. Dispatch `publish.yml` with `ref=v1.0.0`. This first stable release does not require another RC after the earlier `rc.1` bootstrap.
2. For subsequent releases, use Conventional Commits. Release Please opens a draft PR updating both manifest versions and `CHANGELOG.md`; its workflow synchronizes `bun.lock` and marks the PR ready only after that commit succeeds. Review the version and CI checks before merging. GitHub does not trigger PR checks from PRs created with its default `GITHUB_TOKEN`; to avoid manual validation, configure the repository's `RELEASE_PLEASE_TOKEN` GitHub credential. This credential is not an npm token.
3. On `main` pushes while a release PR is open, `release-please.yml` publishes a new prerelease under `next`. Merging that PR tags the reviewed merge commit and dispatches `publish.yml` automatically. Publish validates that stable tag is reachable from `main`, checks local and packed consumers, publishes under `latest`, verifies registry consumers and Promptfoo E2E, then publishes the draft GitHub release.

4. If stable publishing fails before npm publication, the GitHub release remains draft. Rerun `publish.yml` for the same stable tag, or rerun `release-please.yml` if dispatch failed. If npm publication succeeded but registry checks expose a real defect, the npm version is immutable and may already be `latest`: fix the defect on `main`. Release Please can prepare a corrective version PR without promoting the failed draft; after the correction publishes, remove the superseded draft. A transient registry failure may instead be resolved by rerunning the original publish workflow, which verifies the existing version before promoting its draft.

Configure npm trusted publishers for organization `allagentsdev`, repository `promptfoo-integration`, GitHub environment `npm`: `release-please.yml` publishes `next` previews and `publish.yml` publishes stable `latest`, each with direct `npm publish` allowed. Both jobs need `id-token: write` and npm 11.6.2; no npm token is stored in GitHub. See [npm's trusted-publishing setup](https://docs.npmjs.com/trusted-publishers/).

The initial `1.0.0-rc.1` was published manually without provenance. npm assigned both `next` and `latest` to that first version; stable `1.0.0` will move `latest` to the verified release. The candidate's published repository metadata cannot be changed retroactively.
