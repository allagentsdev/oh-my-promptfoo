# Releasing to npm

Release Please prepares version and changelog pull requests once the current version exists on npm with a published GitHub release. Its [workflow](../.github/workflows/release-please.yml) runs on `main` pushes or manual dispatch and synchronizes `bun.lock` in each updated release PR. It does not tag releases or publish npm packages. Only the GitHub-hosted [Publish workflow](../.github/workflows/publish.yml) publishes with npm OIDC and provenance. Publish checks the requested release tag, runs the source and packed Promptfoo gates, then verifies the exact registry version with consumer and Promptfoo E2E checks. Repeating a successful workflow verifies the existing version and dist-tag without republishing.

1. For the first stable release, confirm the root and public package manifests both contain `1.0.0` at the reviewed commit. Release Please waits until this version has been published and has a matching GitHub release.
2. Create and push a new release-candidate tag at that commit, for example `v1.0.0-rc.2`. Dispatch `publish.yml` with `ref=v1.0.0-rc.2`. The workflow stamps the RC version only in its working tree and publishes it under `next`; do not reuse the candidate from the earlier commit.
3. After the candidate's registry consumer and built Promptfoo E2E checks pass, create and push `v1.0.0` at the same reviewed commit. Dispatch `publish.yml` with `ref=v1.0.0`. It checks the matching `next` candidate, publishes stable under `latest`, then verifies registry consumers and E2E again.

4. For subsequent releases, use Conventional Commits. Release Please opens a draft PR updating both manifest versions and `CHANGELOG.md`; its workflow synchronizes `bun.lock` and marks the PR ready only after that commit succeeds. Review the release version and CI checks before merging. On the next workflow run after a stable release, it marks the merged PR as tagged before preparing another version. GitHub may require manual approval to run checks on PRs created with `GITHUB_TOKEN`; an optional `RELEASE_PLEASE_TOKEN` GitHub credential allows those checks to run automatically. This credential is not an npm publish token.

5. At the merged release PR commit, tag and dispatch a new `vX.Y.Z-rc.N` under `next`, then tag and dispatch `vX.Y.Z` under `latest` at that same commit after the candidate passes. Publish verifies that the candidate tag points at the stable tag's commit; Release Please does not bypass either validation gate.

The npm trusted publisher for `@allagents/promptfoo-integration` authorizes GitHub Actions in organization `allagentsdev`, repository `promptfoo-integration`, workflow filename `publish.yml`, environment `npm`, with direct `npm publish` allowed. `publish.yml` uses `id-token: write` and npm 11.6.2; no npm token is stored in GitHub. `release-please.yml` only needs GitHub permission to prepare PRs, not npm publishing access. See [npm's trusted-publishing setup](https://docs.npmjs.com/trusted-publishers/).

The initial `1.0.0-rc.1` was published manually without provenance. npm assigned both `next` and `latest` to that first version; stable `1.0.0` will move `latest` to the verified release. The candidate's published repository metadata cannot be changed retroactively.
