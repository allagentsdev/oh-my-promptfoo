# ADR 0006: Name llmAssert's suite instructions rubricPrompt and keep the system prompt fixed

- Status: Accepted; answer placement amended by [ADR 0011](0011-llm-assert-is-batched-llm-rubric.md)
- Date: 2026-10-21

## Context

`llmAssert` scored criteria from `config.components` and took extra suite text in `config.rubric`, added under an `Additional grading guidance` heading. Promptfoo uses "rubric" for the criteria themselves: `llm-rubric` passes its `value` into the template as `{{ rubric }}`. A Promptfoo user reading `rubric:` here expects criteria and gets instructions. One consumer's shared YAML anchor, named after binary scoring but holding scope notes, shows the confusion in practice.

`config.components` values and the suite text were also passed to the judge verbatim. Promptfoo renders an assertion's `value` with the test's variables but hands its `config` to a JavaScript assertion unrendered, so `{{ source }}` reached the judge as literal braces. Promptfoo's own guidance for faithfulness rubrics is to inline the source through a variable, which silently did nothing here.

## Decision

Rename `config.rubric` to `config.rubricPrompt`, and render test variables in it and in every component `value`.

- **One name for the knob Promptfoo users already know.** `rubricPrompt` is what they reach for to change how the grader judges. Unlike `llm-rubric`, it never replaces the system prompt. One request can score every criterion only because the reply format is fixed, so the suite's text is added beneath the built-in rules under a heading that says it cannot change them. There is no full-replacement mode, so the name cannot later acquire a second meaning.
- **Reject incompatible templates and types.** The answer is always sent to the judge on its own as the user message, and the criteria come from `components`. A `rubricPrompt` or component that uses `{{ output }}` or `{{ rubric }}` fails because those slots belong to a whole-prompt `llm-rubric` template. A non-string `rubricPrompt` also fails: chat arrays, inline objects, and parsed JSON/YAML file contents cannot replace the fixed prompt. The assertion cannot infer which source produced an object or array.
- **Render with Promptfoo's conventions, not its private runtime state.** Resolve Nunjucks from the installed Promptfoo peer rather than bundle a second copy. Both criteria and `rubricPrompt` receive test variables, the process-level `env` global, and `load`, whose implementation is exactly `JSON.parse`. Criteria retain structured variables for property access. Only `rubricPrompt` applies Promptfoo's grader conversion: non-null objects become JSON strings; arrays remain arrays, with non-null object elements converted to JSON strings and primitive elements unchanged. `PROMPTFOO_DISABLE_OBJECT_STRINGIFY=true` or `1` preserves structured variables there too. An unset variable fails before any judge request. `PROMPTFOO_DISABLE_TEMPLATING=true` or `1` leaves both text fields literal. The strict-unset and literal-disable rules are deliberate safeguards, not upstream grader defaults.
- **Remove `rubric` outright.** There are no external users yet, so it is not kept as an alias. A config that still sets it fails with a message naming the new key.
- **Keep assertion configuration local.** Only `config.rubricPrompt` supplies suite instructions. Do not read `test.options.rubricPrompt`: that is Promptfoo's shared grading option and may contain a whole-prompt replacement intended for a different assertion. Reuse suite text with YAML anchors and aliases on `config.rubricPrompt` instead.
- **Never guess the config directory.** A `file://` reference that reaches `llmAssert` requires a supported config-directory context. Neither inspected Promptfoo version exposes one to script assertions, so remaining references fail with a clear missing-config-directory error instead of resolving relative to the process working directory. This does not describe references Promptfoo has already loaded: for external tests (`tests: file://*.yaml`, JSON or JSONL), `maybeLoadConfigFromExternalFile` can inline nested `config.rubricPrompt` and component `value` references from its base path before the callback. Loaded strings undergo normal template checks; parsed JSON/YAML objects and arrays fail string-template validation. The callback carries no provenance to distinguish a loaded object from an inline object, so the error names both possibilities without claiming a file origin.

## Consequences

`llmAssert` will never offer a Promptfoo-style whole-prompt replacement. A suite that needs one should use `llm-rubric` directly and accept one judge request per criterion.

The assertion-time process-level `env` global honors `PROMPTFOO_DISABLE_TEMPLATE_ENV_VARS`, defaulting to disabled when `PROMPTFOO_SELF_HOSTED` is enabled; an absent or empty disable flag uses that default, and an explicit false flag overrides it. Boolean environment flags use Promptfoo's case-insensitive true spellings: `1`, `true`, `yes`, `yup`, and `yeppers`. `llmAssert` does not read private config-level or async-scoped environment overrides or custom `nunjucksFilters`. Separately, Promptfoo's `renderEnvOnlyInObject` config-load pass merges config `env:` and can substitute `{{ env.NAME }}` in inline assertion configs before the callback runs. Such text may therefore contain config-level values even though the assertion-time global only supplies the permitted process environment. Assertion rendering flags cannot undo upstream preprocessing. E2E coverage uses `{% set e = env.NAME %}{{ e }}` to defer env access until assertion rendering.

Existing configs that set `rubric` must be renamed when they upgrade. The release is a minor version because the package has no users outside the maintainers' own suites.

## Upstream source findings

Compared Promptfoo **0.122.0** and **0.124.0**:

- The script callback context contains `prompt`, `vars`, `test`, provider details, a structured clone of assertion `config`, and optional metadata/trace; it has no config directory. Upstream's own file loader instead reads private `cliState.basePath`. See [`assertions/index.ts` at 0.122.0](https://github.com/promptfoo/promptfoo/blob/0.122.0/src/assertions/index.ts#L440-L493) and [0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/assertions/index.ts#L446-L499), plus [`loadRubricPrompt` at 0.122.0](https://github.com/promptfoo/promptfoo/blob/0.122.0/src/matchers/rubric.ts#L60-L109) and [0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/matchers/rubric.ts#L61-L110). Importing private CLI state or falling back to `cwd` is not a supported context contract.
- Both versions register `load` as `JSON.parse(str)`, without file loading or error recovery. At 0.122.0, `env` merges permitted `process.env` with config `env` (config wins); only process access is gated by `PROMPTFOO_DISABLE_TEMPLATE_ENV_VARS`, defaulting to `PROMPTFOO_SELF_HOSTED`. At 0.124.0, a proxy reads async-scoped overrides first, then permitted file-scoped/process values. See [`util/templates.ts` at 0.122.0](https://github.com/promptfoo/promptfoo/blob/0.122.0/src/util/templates.ts#L430-L469) and [0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/util/templates.ts#L421-L514). The newer version combines process-, file-, and suite-level restrictions so a suite cannot lift an operator restriction: [`envars.ts` at 0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/envars.ts#L543-L563). `llmAssert` supports the process-level subset, not the private configuration/async state.
- Both versions' `processContextForTemplating` perform the object/array conversion described above only in the grader-prompt renderer. `PROMPTFOO_DISABLE_OBJECT_STRINGIFY` bypasses that conversion. See [`matchers/rubric.ts` at 0.122.0](https://github.com/promptfoo/promptfoo/blob/0.122.0/src/matchers/rubric.ts#L112-L160) and [0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/matchers/rubric.ts#L113-L161). Arrays are not converted wholesale to JSON strings. Use `{{ source | load }}` to recover a stringified object for property access, or disable conversion to access structured variables directly.
- Upstream's grader engine is created with `getNunjucksEngine(undefined, false, true)`, so undefined values do not throw by default and grader mode bypasses `PROMPTFOO_DISABLE_TEMPLATING`; `llmAssert` intentionally differs on both points. See [`rubric.ts` at 0.122.0](https://github.com/promptfoo/promptfoo/blob/0.122.0/src/matchers/rubric.ts#L30) and [0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/matchers/rubric.ts#L30), together with the template-engine sources above. Boolean parsing accepts `1`, `true`, `yes`, `yup`, and `yeppers` case-insensitively in both Promptfoo and `llmAssert`: [`envars.ts` at 0.122.0](https://github.com/promptfoo/promptfoo/blob/0.122.0/src/envars.ts#L500-L508) and [0.124.0](https://github.com/promptfoo/promptfoo/blob/0.124.0/src/envars.ts#L543-L551).
